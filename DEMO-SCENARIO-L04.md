# Демо-сценарій — Тема 4: MCP-сервер (лабораторна) + Blast Radius (домашня)

Покроковий сценарій для запису відео. Усі id нижче — **справжні, з вашої локальної бази**,
тож їх можна копіювати як є.

Орієнтовний хронометраж: **9–12 хвилин** (лабораторна ~6, домашня ~4).

---

## Що показуємо і чим це відрізняється від інструкції викладача

Дві розбіжності, які краще назвати вголос на відео, ніж дати глядачеві помітити їх самому:

| В інструкції | У нас | Чому |
|---|---|---|
| `list_agents`, `get_findings`, … | `devdigest_list_agents`, `devdigest_get_findings`, … | Префікс `devdigest_` — інструментів у сесії багато, і префікс не дає зіткнутися іменам. Інструментів рівно 5, як і вимагається. |
| `run_agent_on_pr(agent_id, pr_id)` | поле називається `agent`, не `agent_id` | Значення те саме — id агента з `list_agents`. В Inspector ви заповнюєте форму, тож просто вписуєте id у поле `agent`. |

`pr_id` і `repo_id` працюють точно так, як в інструкції. Наш сервер приймає **два способи
адресації** — `pr_id` (uuid зі студії) і пару `repo` + `pr` (номер PR на GitHub). Це варто
показати: спочатку викликати як в інструкції (`pr_id`), а потім один раз — семантично.

# ЧАСТИНА 1 — Лабораторна: MCP Inspector

## 1.1 Запуск Inspector

Кажемо вголос: «MCP-сервер — це stdio-процес, його запускає клієнт. Inspector — і є той
клієнт, яким ми перевіряємо, що всі інструменти справді працюють.»

```bash
cd ~/Work/dev-digest/mcp-server
npm run inspect
```

> Це те саме, що команда з інструкції (`npx @modelcontextprotocol/inspector tsx src/index.ts`),
> тільки через `../scripts/mcp.sh` — лаунчер, на який дивиться і Claude Code через
> `.mcp.json`. Якщо хочете буквально як в інструкції, працює й вона.

**Показати на екрані:** у терміналі з'явиться URL із токеном сесії. Відкриваємо його
(або `http://localhost:6274`).

## 2.3 Символи → викликачі (головна вимога завдання)

Перший рядок дерева вже розкритий. Показуємо:

- `createTask()` з підписом файлу `src/modules/tasks/service.ts`
- під ним викликач: `src/modules/tasks/routes.ts:10`

Потім **розкриваємо другий `createTask()`** — той, що з `src/modules/tasks/repo.ts`:

- його викликач інший: `src/modules/tasks/service.ts:11`

Це найсильніший момент демо, і його варто проговорити:

> «Однакове ім'я `createTask` оголошене у двох шарах — у репозиторії й у сервісі. Це не
> дублікат: у кожного свій викликач, і карта показує реальний ланцюжок цього коду —
> `routes.ts` викликає `service.ts`, а `service.ts` викликає `repo.ts`. Тому поруч з іменем
> показано файл — рівно тоді, коли ім'я в карті повторюється.»

## 2.4 Клік на `файл:рядок` (окремий критерій приймання)

Клікаємо на `src/modules/tasks/routes.ts:10`.

**Показати:** відкривається GitHub рівно на цьому рядку.

Кажемо: «Посилання прив'язане до коміта, на якому будувався індекс, а не до HEAD гілки PR.
Викликачі — це файли, яких PR не змінює, і їхні номери рядків виміряні саме на тому дереві.»

## 2.5 Зачеплені ендпоінти

Показуємо блок бейджів — п'ять реальних маршрутів:

```
GET /projects/:projectId/tasks
POST /projects/:projectId/tasks
GET /projects/:projectId/tasks/:id
PATCH /projects/:projectId/tasks/:id
DELETE /projects/:projectId/tasks/:id
```

Наводимо курсор на бейдж — у підказці видно файл, який його оголошує.

Кажемо: «Ендпоінти знайдені двома шляхами: через файли, де є викликачі символів, і через
**зворотний обхід графа імпортів** — хто імпортує змінений файл, максимум два кроки.
Напрямок принциповий: показуємо тих, хто залежить від зміни, а не залежності самої зміни.»

## 2.6 Вкладка Graph

Перемикаємо **tree → graph**.

**Показати:** той самий граф як діаграма, стрілки йдуть у бік поширення впливу:
символ → викликач → ендпоінт.

## 2.7 Порожній і неповний стани (сильний фінал)

Це те, що відрізняє карту впливу від оманливої карти. Відкриваємо PR у репозиторії, який
не проіндексований — `acme/payments-api`:

```
http://localhost:3000/repos/0544e257-f2ae-4778-92eb-8370871317c3/pulls/482
```

**Що саме побачите** (перевірено): `status: degraded`, `reason: index_missing`, усі
чотири числа — нулі.

**Показати:** картка не мовчить. Вона каже, що індексу немає, і прямим текстом — що це
**не** означає відсутність впливу, бо аналіз просто не виконувався. Числа при цьому видно
(нулі), а не сховано.

Кажемо фінальну фразу:

> «Порожня карта може означати три різні речі: цей код справді ніхто не викликає; індекс
> покриває лише частину репозиторію; або аналіз узагалі не виконувався. Якби всі три
> малювалися однаково — фіча була б шкідливою. Тому статус і причина завжди приходять
> разом із картою.»
